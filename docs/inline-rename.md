# 就地改名（@變數）

本頁說明查詢視窗「就地改名」的操作方式與作用範圍——把游標所在的 `@變數` 連同同一批次
裡的其他出現位置一起改掉。只是要整理物件名稱或 `TOP` 的話見[文字改寫](text-rewrites.md)。

判斷哪些位置算同一個變數全部在 `SqlAssist.Core.Rewriting.SqlVariableRename`，只看文字、
不連線；`Ssms22/Commands/InlineRenameCommand` 只負責取焦點、選取、畫底色與寫回緩衝區。

## 操作

| 動作 | 結果 |
|---|---|
| 游標停在 `@變數` 上，按命令或 `F2` | 名稱被選取，其他出現位置加上底色 |
| 直接打字 | 每一次按鍵都同步到其他出現位置 |
| `Enter`，或焦點離開編輯器 | 提交 |
| `Esc` | 整批還原 |

選取的是 `@` **之後**那一段：`@` 是語法的一部分，一起選起來的話第一個字就會把它吃掉。
提交失敗（名稱不合法、撞名）時不還原、也不跳對話框，改名模式留著讓使用者再修一個字，
原因寫在狀態列——那個當下他的鍵盤還在編輯器上。

## 範圍是一個批次

`DECLARE` 與變數同屬一個批次，跨過 `GO` 之後同名的 `@變數` 是另一個變數。跨批次一起改
會讓第二個批次憑空多出一個沒有宣告的名稱，而錯誤要到執行那一段才出現。

批次界線取自 ScriptDom 判定的 `Go` 權杖，**不是找 `GO` 這個字**：字串常值裡的 `'GO'`、
註解裡的 `-- GO` 與資料行名稱 `[GO]` 都不是分隔。當成分隔的話批次會被切在它們身上，
症狀是「有幾處沒改到」——而使用者看得到的地方每一處都對，要捲到很後面才發現。

## 不跟著改的位置

| 位置 | 例子 | 為什麼 |
|---|---|---|
| 系統函式 | `@@ROWCOUNT`、`@@ERROR` | 不是宣告出來的東西，改了只會讓那一段失效 |
| 被呼叫程序的參數名 | `EXEC dbo.P @p = 1` 的 `@p` | 名字由程序的簽章決定，跟著改會讓那次呼叫找不到參數 |
| `EXEC` 之後的新敘述 | `EXEC dbo.P @p = 1` 後面的 `SELECT @x = …` | 參數清單沒有結束標記，掃描得停在下一道敘述的起頭 |
| 字串與註解 | `'@p'`、`-- @p` | 那裡不是變數 |

`EXEC @rc = dbo.P @p = 1` 的 `@rc` **可以**改：等號右邊才開始是程序的參數，它自己是接
回傳值的區域變數。它與 `@p` 長得一模一樣，差別只在程序名稱的哪一側，所以掃描要分兩段。

## 為什麼分成兩顆命令

命令的可用狀態掛在 ID 上，而兩顆要的狀態不同：

| 命令 | 命令名稱 | 什麼時候可用 |
|---|---|---|
| 查詢視窗右鍵 | `SqlAssist.InlineRename` | 游標停在可以改名的變數上 |
| `F2` | `SqlAssist.InlineRenameKey` | 再加上鍵盤真的在 SQL 編輯器上 |

`F2` 在 SSMS 是「重新命名物件總管的節點」，而命令表的鍵繫結只能用全域範圍。
「最後拿過焦點的 SQL 編輯器」與「現在有焦點的那一個」是兩件事——共用一個 ID 的話，
使用者在物件總管按 `F2` 會被搶走，改的還是查詢視窗裡的變數，畫面上看不出關聯。
停用的命令殼層不派送，所以多這一個條件就讓那些地方的 `F2` 照常落回原本的用途。
