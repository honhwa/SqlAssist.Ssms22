# F12 的物件指令碼

本頁只處理不同物件要產生哪一種定義；開窗與執行緒見[移至定義](go-to-definition.md)。

## 產生出來的是什麼

| 物件種類 | 內容 |
|---|---|
| 預存程序、函式、觸發程序、檢視 | `OBJECT_DEFINITION` 的原文，開頭的 `CREATE` 改寫成 `ALTER` |
| 資料表 | 重建的 `CREATE TABLE`，後面接索引、條件約束、外來鍵與擴充屬性 |
| 資料表型別 | 重建的 `CREATE TYPE ... AS TABLE`，主索引鍵寫成不具名的內嵌條件約束 |
| 取不到定義的模組 | 整段註解，寫明兩個可能的原因與查得到的欄位、參數 |
| 取不到欄位的資料表、資料表型別 | 整段註解，寫明兩個可能的原因 |
| 同義字、序列 | `CREATE SYNONYM`、`CREATE SEQUENCE`（維持 CREATE，這兩種沒有整體的 ALTER 寫法） |
| 條件約束（`CHECK`／`DEFAULT`／主索引鍵與唯一鍵／外來鍵） | 父物件上的那一句 `ALTER TABLE … ADD CONSTRAINT`，見下節 |
| 認不出來的種類 | 整段註解，寫明為什麼組不出可執行的指令碼 |

前五列與浮動預覽的**指令碼**分頁是同一份，連排版都同一份
（[structure-preview.md](structure-preview.md)、[指令碼產生](script-generation.md)）：
差別只在 F12 那一條多蓋了四個選項。

那四項是可執行性的要求，不是風格偏好，所以不管使用者選了哪一組風格都要蓋掉：
開頭先用 `USE` 指名資料庫、批次分隔、`SET` 選項，以及模組寫成 `ALTER`。
`ALTER PROCEDURE` 必須是批次裡的第一個敘述，所以它後面一定要有 `GO` 才分得開；
而計算欄位、篩選索引與索引檢視對那兩個 `SET` 的值有要求，少了它們的 `CREATE TABLE`
在某些連線設定下會直接失敗。

## 開頭先指名資料庫

第一個批次是指名資料庫，不是 `SET`：

```sql
USE [LibArchive]
GO
SET ANSI_NULLS ON
GO
```

新的查詢視窗只沿用**來源**視窗那條連線（見[移至定義](go-to-definition.md)），
而定義本身不帶資料庫。少了這一行，游標停在 `LibArchive.dbo.usp_Loan_Renew` 按 F12
之後再按 F5，改的是目前資料庫裡同名的那一個——或直接失敗，而畫面上看不出差別。
所以它與其他三項同一類，由 `SqlScriptPreferences.CreateForExecution` 蓋上去。

三件事刻意這樣：

- **方括號不是排版。** 它由 `SqlIdentifier.Quote` 加，跳脫規則與其他識別字同一份。
  資料庫名稱不保證是合法的識別字，而 `USE` 沒有第二種能補救的寫法。
- **連結伺服器上的物件不寫。** `USE` 只換得動本機連線的資料庫，寫了會切到本機同名的
  資料庫——比不寫更糟，因為它會安靜地成功。那種定義要 `EXEC … AT` 才執行得了，
  那不是這一行解決的問題（[跨伺服器中繼資料](metadata-remote.md)）。
- **唯讀的預覽不寫。** 浮動預覽的指令碼分頁與 SQL Search 的預覽面板顯示的是「這個
  物件的定義」，而 `USE` 不屬於定義；`IncludeDatabaseContext` 在那兩條路上維持預設
  的關閉。它改的是新視窗要用哪個資料庫，那是執行的事。

名稱取自物件自己（`SqlObjectInfo.DatabaseName`）。同一條連線的物件帶的是查詢視窗
選取的那一個，所以那一次寫出來的與不寫的結果一樣，差別只在指令碼被複製到別的視窗
之後仍然跑到對的資料庫。連線還沒選定資料庫、或物件是指令碼自己宣告的暫存資料表與
資料表變數時都沒有名稱可寫，那時靜靜地不寫。

缺資料時整段換成註解的輸出**不會**有這一行：那一段不是 T-SQL，前面多一行可以執行的
`USE` 就讓它看起來像一份跑得起來的指令碼，而那正是那一段唯一的保證。

`SET` 的值依 `sys.tables` 反推建立當時的那一組，不是固定寫 `ON`：一張在 `OFF`
之下建起來的資料表，用 `ON` 重建可能直接失敗——而失敗還算好的，計算欄位的
運算式在兩種設定下算出不同結果才是真的難查。

模組改寫成 `ALTER` 是在**定義本身**上做的，不是等整份組完再改：`SET` 開著時
那一份的開頭是 `SET ANSI_NULLS ON`，改寫會一律失敗而沒有任何徵兆。

### 為什麼是 ALTER 而不是 CREATE

F12 之後接著要做的事幾乎都是「改一下再執行」。給 `CREATE` 的話每一次都要自己把
第一個字改掉，而那正是提交建議時 `ap` 展開成完整 `ALTER` 定義已經在做的事
（[整句展開](statement-expansion.md)）——兩條路徑對同一個模組給出不同的開頭關鍵字，
只會讓人以為其中一條壞了。

資料表與資料表型別**不**改寫：`ALTER TABLE` 沒有整體寫法，`ALTER TYPE` 不存在。

### 條件約束寫的是父物件

條件約束身上沒有自己的定義：`DEFAULT` 的運算式在資料行上，`CHECK` 的條件、鍵的
資料行與外來鍵的參照都在父物件的第四層裡。所以這一種先問出父物件是誰
（`SqlMetadataQueries.ConstraintParent`），再走**同一個** `GetStructureAsync` 把那張表
的結構載回來，掛在 `SqlObjectStructure.Parent` 上；四種寫法一個字都不另外組，
全部走資料表那條路徑上既有的那幾支。另寫一組「條件約束專用」的查詢與排版，症狀是
同一個外來鍵在「整張表的指令碼」與「只要這一條」長得不一樣。

名稱一律寫出來，即使風格說要省略系統配的名稱（`Minimal`）：使用者要的就是這一個
名字的定義，省掉之後交出去的是一段「某個沒有名字的條件約束」，貼上去會由引擎再配
一個新名字。`SET` 選項取父物件那一份——`CHECK` 的運算式與計算資料行一樣受那兩個
選項影響。

父物件讀不到（卸除、權限被收回、第四層查詢失敗）或那張表上沒有這個名稱時**整段
換成註解**，兩種各寫各的原因：前者要去看那張表，後者要去重新整理清單。
同義字也沒有整體 `ALTER`；`ALTER SEQUENCE` 則改不了型別。硬改只會讓指令碼執行失敗。

### 為什麼還留著「整段註解」這一支

只剩 `SqlObjectKinds.FromSysObjectType` 認不出來的種類會走到那裡。這一支不能拿掉：
沒見過的型別代碼一律對應到 `Unknown`，而 SQL Server 的物件型別只會愈來愈多，
硬湊一份指令碼出來就是指令碼在說謊。

同義字、序列與資料表型別曾經都在這一列。前兩者的定義其實就是目錄檢視上的那幾個
欄位（`sys.synonyms.base_object_name`、`sys.sequences` 的界限與快取），
現在由 `Metadata/Formatting/SqlCatalogScript` 組回 `CREATE`，見
[metadata.md](metadata.md)。資料表型別則有欄位，不擋掉會被寫成 `CREATE TABLE`，
照著執行會多出一張同名的資料表——而它需要的 `CREATE TYPE ... AS TABLE` 查得到的
資料就組得出來，所以現在直接組，三種都不必再繞。

「哪一類寫得出可以執行的指令碼」由 `SqlObjectKinds.HasExecutableScript` 一份說了算，
這條路徑與浮動預覽的指令碼分頁共用。各留一份判斷的症狀已經發生過一次：同一個
資料表型別，F12 給註解，預覽卻給 `CREATE TABLE`。

種類過得了關、這一次的資料卻不齊時（模組沒有定義、資料表沒有欄位、第四層查詢
失敗），
註解是 `SqlObjectStructure` 那一端換的，這裡原樣帶出來——那一份寫的是缺什麼與
為什麼，與上面「這一類物件本來就組不出來」是兩件事。判斷同樣只有一份，
見 [metadata.md](metadata.md)。
