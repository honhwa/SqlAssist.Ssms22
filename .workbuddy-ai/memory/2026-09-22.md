## 修 bug：宣告行多一個 `OUTPUT`（已完成並通過測試）

回報症狀：`DECLARE @cond varchar(8000) OUTPUT = '' OUTPUT;`——同一個關鍵字出現兩次。

**根因不在 `SqlProcedureCallText`**（它只寫一次 `OUTPUT`，在型別之後），而在讀預設值那一側：
`SqlModuleParameterDefaults.TryReadDefault` 不認 `OUTPUT`／`OUT`／`READONLY` 這三個參數修飾詞，
而它們**可以寫在等號前面**：

```text
@cond VARCHAR(8000) OUTPUT = ''      -- 修飾詞在等號前 → 被讀成「沒有預設值」
@Result INT = 0 OUTPUT               -- 修飾詞在等號後 → 切出 "0 OUTPUT"
```

第二種情形切出來的值被原樣填進宣告行，就成了回報的那個句子。修法是兩處都要認這三個字：
- 找等號的迴圈：遇到修飾詞 `continue`（跳過），否則 `@X INT OUTPUT = 0` 的等號永遠找不到。
- 切值的迴圈：`current == depth && IsParameterModifier(token)` → `break`。
  位置必須在「收尾右括號算進值裡」那兩條**之後**，否則 `GETDATE()` 會被切壞。
- 新增 `IsParameterModifier(SqlToken)` 私有 helper；用 `SqlToken.IsKeyword` 判定，
  加了引號的同名識別字（`[output]`）自動被排除。

`Find` 與 `FindValues` 共用同一條路徑，所以「選擇性」清單一起修好了。

## 修正：OUTPUT 位置放錯 + 預覽也要高亮（第二輪）

**問題一：`OUTPUT` 的位置本身就是語法錯誤。**

第一輪只修了「關鍵字出現兩次」，沒發現真正的位置是錯的。T-SQL 的宣告語法是
`DECLARE @變數 型別 [= 值]`，而 `OUTPUT` 是參數修飾詞，**只能緊跟在型別之後**：

```text
DECLARE @NewDueDate datetime2(7) OUTPUT = NULL;   -- 對
DECLARE @NewDueDate datetime2(7) = NULL OUTPUT;   -- 語法錯誤
```

`AppendDeclarations` 原本把 `" OUTPUT"` 接在型別之後、但把 `" = " + 值` 也接在同一串，
重排一下就好：型別 → 修飾詞 → `= 值;`。測試 `OUTPUT寫在等號之前` 取代了原本的
`宣告行只寫一次OUTPUT`（後者只驗「不會出現兩次」，驗不到位置）。
新增 `沒有預設值的OUTPUT參數修飾詞在值之前` 釘住「沒有預設值時修飾詞仍然在等號前」。

**問題二：預覽的高亮與清單不同色，而且那個色被校正成橄欖色。**

`ScriptResource.Highlight` 本來由主題**強調色**推導（`AccentBorder` 疊 0x59），
而清單上的記號是**黃**——同一件事在兩處標成兩個顏色，使用者會以為它們指涉不同東西。
改成同一個黃之後，**又踩到一個坑**：`ThemeColorMath.EnsureBackgroundForText` 不能拿來處理這個輸入。

那一支是為「使用者自訂的固定字色」寫的：它往黑或白疊一層灰，直到**最淡的著色**（註解色）
在高亮上也讀得到。拿黃當輸入時那個條件太鬆——黃本來就亮，疊 16% 的黑就過了 4.5:1，
而疊完已經是 `#998C4C` 這種**橄欖色**。實測 light／dark／plum／forest／mango 五種底色
全部如此，也就是預覽裡的標記跟清單上那個黃看起來是兩回事。

改法：`Fade(mark, background)` 疊一層**限量**的半透明黑或白（每階 10%、上限 60%），
只動明度不動色相；校正目標從「文字 4.5:1」改成「記號與指令碼底色 3:1」（非文字的圖形對比）。
方向由「底色與黑、與白哪個比較遠」判斷（`Luminance` 在 `ThemeColorMath` 是 private，不另外暴露）。
結果：淺色底壓成 `#998000`（對比 3.86）、深色底提亮成 `#FFDA1A`（對比 10~12），
兩邊都還是認得出的黃。

## 模組指令碼最前面補 USE（第三輪）

需求：對程序或函式執行「移至定義」時，最前面先 `USE [物件所在的資料庫]` + `GO`，
再顯示完整內容。使用者另外指定範圍是**所有模組**（程序、函式、檢視、觸發程序），
而且**預覽也要跟著加**（不只開出來的查詢視窗）。

設計：規則只落在 `TSqlScriptRenderer.AppendDatabaseContext` 一處。三個表面全部匯到
同一個 renderer——`SqlDefinitionScript`（F12 與 SQL Search 啟動）、
`SqlSearchDefinitionLoader`（定義預覽）、`SqlStructurePreviewControl.GetScript`
（浮動預覽指令碼分頁）——所以在 renderer 加就一次蓋到三邊。

關鍵判斷（都是踩過才知道的）：

- **閘門是「模組」不是「要執行」**。模組的定義是存在資料庫裡的一份文件，`ALTER` 它
  就是在改那一份，跑錯資料庫等於蓋掉別人的同名程序；`CREATE TABLE` 則是可以拿到任何
  地方執行的樣板，釘住來源資料庫反而擋掉「把這張表編寫到另一個資料庫」。所以
  `SqlScriptPreferences` 只開 `IncludeDatabaseContext`，模組判斷留在 renderer——
  也才測得到（`SqlScriptPreferences` 依賴 `SqlAssistSettingsStore`，編不進測試專案）。
- **`requiresBatch: true` 不可省**。模組必須是批次裡的第一個敘述；`BatchSeparation.None`
  時 `batched: true` 不補 `GO`，只有 `RequiresBatch` 會，少了它整份執行不了。
- **排在檔頭註解之前**（使用者說「最前方」）；檔頭關著時（預設）它就是第一行。
- `DatabaseName` 為空時整句不寫。**F12 路徑上它不是 null**：本機目錄的 `LoadSnapshot`
  用 `_qualifier.DatabaseName ?? _connectionSource.DatabaseName` 蓋章，連線自己的
  資料庫也拿得到名字。`SqlObjectInfo` 上「為 null」那句指的是建議清單那條自己 new
  的路徑，而那裡只有非模組。
- **游標落點要跟著改**：`SqlObjectScript.SkipLeadingSetBatches` 更名為
  `SkipLeadingPreamble` 並加認 `USE `，否則 F12 每次都停在整份指令碼第一個字元。

## 更正：`(NULL)` 的真因不是 P 盤未掛載，且已在 14:10 完整修復

修復步驟（實測可行，取代上面第 64–75 行那版）：

1. 從 reflog 找回 SHA：`git --git-dir=P:/github/SqlAssist.Ssms22/.git log -g --all`。
