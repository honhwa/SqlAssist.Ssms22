## EXEC 展開四項需求（已完成並通過測試）

需求：展開 EXEC 時（1）依參數型別自動填預設值、（2）儲存程序有預設值時優先採用、
（3）不論是否 OUTPUT 一律先 `DECLARE`、（4）結尾加 `SELECT` 顯示全部 OUTPUT 參數。

改動 6 檔（核心在 `SqlProcedureCallText` 與 `SqlModuleParameterDefaults`）：

- `SqlModuleParameterDefaults`：`Find` 之外新增 `FindValues(string?) → IDictionary<string,string>`
  取「參數 → 預設值原文」。`sys.parameters.has_default_value` 對 T-SQL 模組永遠是 0
  （只對 CLR 模組有效），所以必須從 `OBJECT_DEFINITION` 用 tokenizer 解析。
  `TryReadDefault` 以同層 `=` 為界，切原文（不用 token 重組），保住 `N'...'`、`''` 轉義、負號。
  **關鍵陷阱**：值掃描遇到 `)` 時不能一律 `--current < depth → break`，
  否則 `GETDATE()` 會被截成 `GETDATE`、`(0.05)` 截成 `(0.05`，生成的宣告是語法錯誤。
  正確寫法：`(` 記 `end`；`)` 在 `current == depth` 時「這個右括號仍屬值」記 `end` 後 break，
  否則 `--current` 並記 `end`。
- `SqlProcedureCallText`：`AppendOutputDeclarations` → **`AppendDeclarations`**（全部參數都宣告，
  OUTPUT 保留 `OUTPUT`，值為 `InitialValue(parameter)`）；新增 `AppendOutputSelect`（空行 + 多行
  `SELECT @X AS X`，別名去 `@`）；`InitialValue` 優先用 `parameter.DefaultValue`，否則
  `SqlLiteralDefaults.ForType`；`Assignment` 兩側都改成變數名（`@X = @X` / `@X = @X OUTPUT`）。
  **縮排陷阱**：被替換的區段從 `EXEC` 起算，行首空白留在緩衝區裡，所以
  **第一行宣告不加 `indent`、後續行才加**。先前寫成「每行都加」會把第一行縮排兩次。
- `SqlStatementParameter`：新增 `string? defaultValue`（空字串正規化為 null）與 `DefaultValue`。
  它回答「先填什麼」，與 `IsOptional` 回答「能不能整列刪掉」是兩件事。
- `SqlCommitExpansions.SqlProcedureCallExpansion.Build`：改用 `FindValues` 接線。

驗證：`SqlProcedureCallTextTests` 10/10、`SqlModuleParameterDefaultsTests` 21/21 全綠；
全套 3774 中 3771 過、3 敗皆為既有紅燈（見下）。

## 根因：NuGet restore 的 `path1` null —— 沙箱剝掉 `PROGRAMFILES(X86)`

長期卡住的 `NuGet.targets(782,5): error : Value cannot be null. (Parameter 'path1')` 已破解。
**反編譯 `C:\Program Files\dotnet\sdk\10.0.401\NuGet.Common.dll` 的 IL** 得到完整鏈路：

```
GetRestoreSettingsTask.Execute()
  → XPlatMachineWideSetting..ctor()
    → NuGetEnvironment.GetFolderPath(NuGetFolderPath.MachineWideConfigDirectory)
      → Path.Combine(Environment.GetEnvironmentVariable("PROGRAMFILES(X86)"), "NuGet", "Config")
```

把 `CalculateFolderPath` 的 switch 表（8 個 case）逐條反組譯後確認：
case 1（MachineWideConfigDirectory）＝ `PROGRAMFILES(X86)` + `["NuGet","Config"]`；
case 0（MachineWideSettingsBaseDirectory）走 `GetHome()`（`DOTNET_CLI_HOME` → `USERPROFILE`）+ `"NuGet"`。
**這個沙箱把 `PROGRAMFILES`／`PROGRAMFILES(X86)`／`PROGRAMDATA`／`ALLUSERSPROFILE`
全部剝掉**，所以 `path1` 是 null。

**解法**：跑 dotnet 前補上這幾個變數（`APPDATA`、`LOCALAPPDATA` 也一起補）。可用腳本：
`artifacts/run_tests.py`（設好 env 後跑整套）、`artifacts/run_focused.py`（只跑指定類別）。
補齊後 `dotnet restore`／`build`／`test` 全部正常，不再需要 `-p:RestoreNoHttpCache` 之類的繞法。

反編譯工具：`python -m pip install dnfile`（裝在 managed python 3.13.12 裡）。
讀 IL 的關鍵：`pe.net.mdtables.TypeDef.rows` → `MethodList` → `m.row.Rva` → 用 section
表換算檔案位移；`#US` 堆要用自己的 compressed-uint 解析器讀（`UserStringHeap` 沒有 `get_string`）。

## ⚠️ 重大陷阱：這台機器上 `git stash` 會刪掉 worktree 註冊

`git stash push` 在這台機器上**會崩潰並刪除 `P:\github\SqlAssist.Ssms22\.git\worktrees\<名>\`
整個目錄**，症狀是之後所有 git 指令回 `fatal: not a git repository: 'P:/…/worktrees/…'`。
崩潰發生在「stash 物件已寫入、但工作區尚未還原」之間 → **檔案不會丟，但索引與 worktree
註冊會消失**。本次踩到兩次。

**修復步驟**（已實測可行）：

1. 建目錄 `P:\github\SqlAssist.Ssms22\.git\worktrees\<worktree 名>\`
2. 寫 `gitdir`（內容＝該 worktree 的 `.git` 檔完整路徑，用正斜線）
3. 寫 `commondir`（內容＝`../..`）
4. 寫 `HEAD`（內容＝`ref: refs/heads/<分支名>`）
5. 若分支 ref 也被刪（`refs/heads/<name>` 不存在），從 `git --git-dir=<主 .git> log -g --all`
   的 reflog 找回 SHA 並重建該檔（**必須用 `rev-parse` 取完整 40 位 SHA，不要自己補尾段**）
6. `git read-tree HEAD` 重建索引（不動工作區檔案）
7. `git stash list` → `git stash drop stash@{0}` 清掉殘留

**結論：這個 repo 上不要再用 `git stash`。** 要做 A/B 比對就先把檔案複製到 `artifacts/backup/`。
