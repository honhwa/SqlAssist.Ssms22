## 新增 F2 變數重新命名（已完成並通過測試）

需求：游標停在變數上按 F2，選取 `@` 之後那一段直接改；改的同時同一上下文裡的同名變數
一起改；↑／↓／Enter 結束；新名與其他變數撞名時禁止修改並提示。

**架構照 F12 那一套走**，兩半分工：

- **Core `Parsing/SqlVariableRename.cs`**（純邏輯，測得到）：`FindAt(sql, caret)` 回
  `SqlVariableRenameTarget`（名稱、名稱起點、每一處的名稱起點、其他變數名），
  `Validate(target, candidate)` 回 `SqlVariableRenameProblem`（None／Empty／
  InvalidName／Duplicate），`IsValidName`。
- **Ssms22 `Editor/SqlVariableRenameSession.cs`**（接線）：選取、`ITextBuffer.Changed`
  鏡射、`Commit`／`Cancel`、靜態 `IsActive` 旗標。

關鍵判斷（踩過才知道的）：

- **範圍取批次（`GO` 邊界）不是敘述、也不是整份指令碼**。區域變數活到批次結束，所以
  「同一個變數」的邊界正好是 `GO`；取整份會把另一個批次裡同名的變數一起改掉。
- **名稱比對不分大小寫**，改完每一處拼法統一成剛打的那一種。
- **字串與註解不算出現處**：靠 `SqlTokenizer.Tokenize`（不含註解多載）本來就不會把它們
  讀成 Variable 詞元，不必另外判。
- **只有 `IsValidName` 過關時才鏡射**：打到一半的 `@a b` 不該留在其他出現處。
- **`@@` 全域變數回 null**：那不是使用者取的名字。
- **命令狀態只問「有沒有 SQL 編輯器」**，不問「游標在不在變數上」——後者要詞法分析整份
  指令碼，而命令狀態每一次按鍵都會被問一次。這是 F12 的同一條界線。
- **`SqlTokenizer.IsIdentifierStart`／`IsIdentifierPart` 由 private 改成 public**，讓
  「這個名字會不會被讀成一個識別字」只有一份答案；自己抄一份字元表遲早對不上。
- **不用 `IMultiSelectionBroker`**（原生、復原一格）：本擴充沒用過它，而這裡沒有 SSMS
  可實測，猜錯等於改壞整份指令碼。只用已經在用且有測試的 `ITrackingSpan`＋一次
  `CreateEdit`／`Apply`＋`Selection.Select`。**取捨是 Ctrl+Z 的粒度**（先還原其他出現
  處、再還原游標那一處），已寫進 `docs/variable-rename.md`。
- 鍵繫結：`Menus.vsct` 全域 `VK_F2` → `cmdidRenameVariable`（`0x021C`）；
  `ProvideMenuResource` 版號 32 → 33。**改了命令表一定要用 `Install-Extension.ps1` 重裝。**
- `netstandard2.0` 的 `string.IsNullOrEmpty` 沒有 `NotNullWhen`，後面直接解參考會報
  誤報的 CS8602；改寫成 `name is null || name.Length == 0`。

### 4. `SqlMemoryVisualTests` 是**平行競態**，不是環境問題（已修）

症狀：單獨跑一定過、整份跑起來必失敗；`Assert.NotNull` 掛在
`VisualTreeHelper.GetDrawing` 回 null。

根因：`SqlIconImage.Factory` 是**行程共用的靜態欄位**，有 **6 個測試類別**在靜態建構子裡
各自換掉它，其中幾個回傳的方塊**沒有背景**（`SqlStateSurfaceTests`、`SqlMemoryUsageViewTests`、
`SqlMemoryCleanupViewTests`、`SqlMemoryRecoveryViewTests`），畫不出東西；
`SqlMemoryVisualTests` 自己那個有 `Brushes.Gray`，它要靠筆墨範圍驗中心線。
xUnit 預設每個類別各自成一個 collection 並行跑，於是工廠被別人蓋掉 → `GetDrawing` null。

驗證手法（值得記）：`--max-threads 1` 就不見了；再用 `--filter-not-class` 把其他 5 個
設工廠的類別逐一排除，留下 `SqlMemoryVisualTests` 時也過 → 指向那 5 個之一。

修法照 repo 既有慣例（`MetadataFailureCollection` 一模一樣的形狀）：新增
`tests/SqlAssist.Ssms22.Tests/UI/SqlIconFactoryCollection.cs`，
`[CollectionDefinition(Name, DisableParallelization = true)]`，
六個類別各掛 `[Collection(SqlIconFactoryCollection.Name)]`。
**要 `DisableParallelization` 而不是只共用一個 collection**：共用只保證那幾個彼此不同時跑，
擋不住第三個類別在工廠被換掉期間建立圖示。連跑三次並行都穩定只剩 1 條失敗。

### 5. 剩下那一條：150% 螢幕縮放，不是產品錯，也還沒決定怎麼修

`NotificationChromeTests.精簡列表進度與覆蓋捲軸且收合切換圖示`。實測本機
`GetScaleFactorForDevice(0) = 150`（`GetDpiForSystem` 回 96 是因為行程不是 DPI-aware）。

根因量化：卡片根 `Border` 是 `BorderThickness="1"` + `UseLayoutRounding="True"`
（`NotificationCard.xaml:5-7`），自動高度因此受邊框捨入影響。150% 下 1 DIP = 1.5 實體像素，
每一邊捨入成 2 px，上下共 4 px = 2.667 DIP，比 2 DIP 多 **0.667** →
`ActualHeight` 量到 188.6667 而設計值是 188。同一份因數也讓
`Assert.Equal(3, bar.ActualWidth)` 量到 2.6667。

**沒有硬改**：把 188 放寬成 `InRange(187,189)` 之後失敗只是往下搬到 298 行的
`Assert.Equal(3, bar.ActualWidth)`——這是**系統性**的，逐條放寬等於一路把契約磨掉。
三條路，需要決定：
(a) 讓這幾條斷言容忍捨入（把精確契約換成區間）；
(b) 在測試宿主把 DPI 釘在 96（例如 `VisualTreeHelper.SetRootDpi`）——精確斷言全部保住；
(c) 接受自動化套件要求 100% 縮放，寫進文件。
注意 `docs/` 把 100%／150%／200% 列為**手動**視覺 QA 的必驗項
（`ui-guidelines.md:93`、`themes.md:115`），而自動化那幾條是自己用
`RenderTargetBitmap` 指定 96/144/192 去掃 DPI 的——所以 (b)/(c) 都說得通。

## 工具：這個 repo 的測試要怎麼跑、怎麼二分（本輪踩出來的）

- **過濾要用 `--filter-class`／`--filter-method`，不要用 `--filter`。**
  測試宿主是 xUnit v3 + Microsoft.Testing.Platform，`--filter` 只吃 **VSTest 語法**
  （`FullyQualifiedName~X`），拿裸類別名進去會回「Zero tests ran」而 exit code 5。
  `--filter-class`／`--filter-method` 吃完整型別／方法名，前後可加 `*`，多個是 OR。
  另有 `--filter-not-class`（多個是 AND）、`--filter-namespace`、`--list-tests`。
- 二分競態：`--max-threads 1`（單執行緒）＋ `--filter-not-class` 逐一排除。
- 直接跑 `tests/<專案>/bin/Release/net48/<專案>.exe` 最快，不必每次都過 `dotnet test`。
- `artifacts/run_full.py` 會把原始輸出留在 `artifacts/full-test-output.txt`（失敗明細在裡面）。
- **`tools/Check-TextFiles.ps1` 在這裡跑不動**：它第一步是 `git ls-files`，而這個
  worktree 的 `.git` 指向沒掛載的 `P:/github/...`。替代做法是自己按位元組驗
  （BOM／`0x0D`／檔尾 LF／UTF-8），本輪 15 個動到的檔案全過。
