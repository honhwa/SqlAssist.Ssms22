需求：游標停在變數上按 F2，選取 `@` 之後那一段直接改；改的同時同一上下文裡的同名變數

**架構照 F12 那一套走**，兩半分工：

關鍵判斷（踩過才知道的）：

- **範圍取批次（`GO` 邊界）不是敘述、也不是整份指令碼**。區域變數活到批次結束，所以
  「同一個變數」的邊界正好是 `GO`；取整份會把另一個批次裡同名的變數一起改掉。
- **名稱比對不分大小寫**，改完每一處拼法統一成剛打的那一種。
- **字串與註解不算出現處**：靠 `SqlTokenizer.Tokenize`（不含註解多載）本來就不會把它們
  讀成 Variable 詞元，不必另外判。
- **只有 `IsValidName` 過關時才鏡射**：打到一半的 `@a b` 不該留在其他出現處。
- **`@@` 全域變數回 null**：那不是使用者取的名字。
- **命令狀態只問「有沒有 SQL 編輯器」**，不問「游標在不在變數上」——後者要詞法分析整份
  指令碼，而命令狀態每一次按鍵都會被問一次。這是 F12 的同一條界線。
- **`SqlTokenizer.IsIdentifierStart`／`IsIdentifierPart` 由 private 改成 public**，讓
  「這個名字會不會被讀成一個識別字」只有一份答案；自己抄一份字元表遲早對不上。
- **不用 `IMultiSelectionBroker`**（原生、復原一格）：本擴充沒用過它，而這裡沒有 SSMS
  可實測，猜錯等於改壞整份指令碼。只用已經在用且有測試的 `ITrackingSpan`＋一次
  `CreateEdit`／`Apply`＋`Selection.Select`。**取捨是 Ctrl+Z 的粒度**（先還原其他出現
  處、再還原游標那一處），已寫進 `docs/variable-rename.md`。

### 5. 剩下那一條：150% 螢幕縮放，不是產品錯，也還沒決定怎麼修

## 工具：這個 repo 的測試要怎麼跑、怎麼二分（本輪踩出來的）

- **過濾要用 `--filter-class`／`--filter-method`，不要用 `--filter`。**
  測試宿主是 xUnit v3 + Microsoft.Testing.Platform，`--filter` 只吃 **VSTest 語法**

- 二分競態：`--max-threads 1`（單執行緒）＋ `--filter-not-class` 逐一排除。
- 直接跑 `tests/<專案>/bin/Release/net48/<專案>.exe` 最快，不必每次都過 `dotnet test`。
- `artifacts/run_full.py` 會把原始輸出留在 `artifacts/full-test-output.txt`（失敗明細在裡面）。

## F2 實機驗收回報的第一個 bug：打成 `@xxxxcond` 且其他出現處沒動

使用者回報：`@cond` 上按 F2、打 `xxxx`、Enter，結果是 `@xxxxcond`，且同一批次的 `@cond` 完全沒跟著改。

### 根因（兩個症狀同一個起點）

`SqlVariableRenameSession.Start()` 先 `Selection.Select(span)`，接著又 `Caret.MoveTo(span.End)`。
**選取之後再動游標會把選取收掉**，游標落在選取範圍的錨點，也就是名稱起點。於是：

1. 使用者打的字是「插在 `@` 後面」而不是取代名稱 → `@xxxxcond`。
2. 主出現處的追蹤區段用 `SpanTrackingMode.EdgePositive`（起點不含插入）。插入發生在它的起點時
   區段被往後推，**區段文字始終等於舊名 `cond`**，`Replace` 每次比較都覺得沒差異 →
   `edit.HasEffectiveChanges == false` → 空操作 → 其他出現處完全沒動。

另外 `Start()` 的註解寫「訂閱放在選取之後」，程式碼卻是先訂閱再選取——註解與程式碼相反。

### 修法（四處，都在 `SqlVariableRenameSession.cs`）

1. `Start()`：先選取、再訂閱（照註解），並**移除 `Caret.MoveTo`**，改用
   `ViewScroller.EnsureSpanVisible(span)` 只捲動不動游標。`Select` 本身已把游標放在範圍末端。
2. 主出現處的追蹤模式 `EdgePositive` → `EdgeInclusive`（兩端都收）。否則「選取被收掉、從名稱
   開頭打」時插入的字落在區段之外，名稱看起來沒變，鏡射變空操作。
3. `OnBufferChanged`：**第一次變更**若是一次純插入（`OldLength == 0 && NewLength > 0`），
   就把插入的文字當成新名稱。判準是「有沒有移除」——選取還在時第一個字是一次取代，有移除也有
   插入，不會誤判。這條讓結果與「選取是否倖存」無關。
4. `OnCaretChanged`：離開界線的起點往左多算一格（變數自己的 `@`）。F2 的進入條件
   （`SqlVariableRename.FindAt`）本來就允許游標停在 `@` 上，界線比它緊的話，殼層把游標還原回
   `@` 時會立刻自我結束，症狀是「按了 F2 卻什麼都沒發生」。

### 驗證

建置 0 警告 0 錯誤；x64 測試 **3905 總計 / 0 失敗**；`Check-Docs` 通過；兩個改動檔的位元組契約
（無 BOM／LF／UTF-8／尾端 LF）通過。

### 這一輪的教訓

**在 `Selection.Select` 之後不要碰 `Caret`。** 這是本功能唯一沒能在開發機驗證的一層，而它就出在
這一層。另外：註解與程式碼不一致時，先相信程式碼——那句註解本來就寫對了意圖，是程式碼寫反了。

### 同一類的第二處：`SqlAutoPairing.TrySurroundSelection`

`Editor/SqlAutoPairing.cs` 有完全一樣的寫法（`Selection.Select(inner)` 之後接
`Caret.MoveTo(inner.End)`）。這裡的選取**是功能的一部分**——`auto-pairing.md` 的四方格表明寫
「把選取的那一段包起來，並保持選取」，用來連包兩層（先 `'` 再 `(`）。選取被收掉之後第二層包不起來，
只會插入一個字元，所以不只是外觀問題。已同樣改成 `ViewScroller.EnsureSpanVisible(inner)`。

**通則升級成護欄**：`docs/rules-platform.md` 新增一條「**禁止**在 `Selection.Select` 之後再呼叫
`Caret.MoveTo`」，寫明兩處症狀（F2 打成 `@xxxxcond`、自動配對包不了第二層）與替代做法。
`docs/auto-pairing.md` 補一節「包完之後選取要留著」，`docs/variable-rename.md` 的同一條加上
指向護欄的連結。

## F2 第二次實機回報：按下 F2 後鍵盤沒有反應（嚴重）

使用者回報「现在进行变量改名在按下F2后键盘直接无回应」。裝的是 1.2.1.1。

### 診斷過程與結論

1. 先讀診斷紀錄檔（`%LocalAppData%\SqlAssist.Ssms22\SqlAssist.log`）：F2 期間**沒有任何**
   `重新命名變數失敗` 這行。但**不能據此排除例外**——`SqlAssistDiagnostics` 是**批次**寫入，
   程式若在批次沖掉之前就卡住，那行永遠不會出現。這一點本身就是個陷阱。
2. 真正說得通所有症狀的機制是：**`Start()` 把 `_active = this` 放在最前面**。之後任何一步
   失敗（新加的 `ViewScroller.EnsureSpanVisible` 是首要嫌疑）就會留下一個「活著、但事件
   處理常式一個都沒掛」的工作階段。而 `SqlShellCommandFilter` 只看 `IsActive` 就認領
   ↑／↓／Enter／Esc——於是那四個鍵**永遠被吞掉**，只能重開 SSMS 才解得掉。
   使用者說「鍵盤沒有反應」，最明顯的就是 Enter 打不出換行。
3. 第二個獨立缺陷：`OnBufferChanged`／`OnCaretChanged` 是**編輯器事件**，卻沒有走
   `SqlAssistPlatformGuard`——`rules-platform.md` 明文要求。從這兩個處理常式丟出去的例外
   會穿進編輯器的輸入管線，症狀同樣是鍵盤整個失效。

### 修法（四道，都在 `SqlVariableRenameSession.cs`）

1. **`_active = this` 與 `_started = true` 移到 `Start()` 的最後**（掛完處理常式之後）。
   `IsActive` 與 `For(view)` 都改成只認 `_started && !_closed`——沒開始完成的工作階段是惰性的，
   認領不到任何按鍵。
2. **`Commit`／`Cancel` 的 `End()` 放進 `finally`**：不管成功、失敗還是例外都會結束。
   因此 **Esc 永遠是使用者的逃生門**。
3. **兩個編輯器事件處理常式改走 `SqlAssistPlatformGuard.Run`**（`Mirror`／`FollowCaret`）。
4. **`ViewScroller.EnsureSpanVisible` 換回 `Caret.EnsureVisible()`**（只捲動，不動游標，也不會
   收掉選取）。`SqlAutoPairing` 一併改成同一個呼叫，兩處一致。

另外加了四行 `WriteAlways` 生命週期紀錄（開始／完成／未套用／取消），其中「開始」那行帶
**選取是否生效**——那是我目前唯一無法從程式碼確定的環節（殼層會不會把選取收掉）。

### 沒動版號（刻意的）

`docs/release.md`：版號 = `version.json` + commit 數，**工作目錄的變更不推進版號**；日常偵錯走

## 順手修掉一條偶發紅燈（第二類：合成輸入讀到 OS 按鍵狀態）

收尾跑整份方案時紅了一條：`SqlMemoryVisualTests.PreviewMetadataStaysSingleLineAndOnlyItsViewportScrolls`
（`tests/SqlAssist.Ssms22.Tests/UI/SqlMemoryVisualTests.cs`）。這條**與 F2 無關**，
`git status` 也確認那一輪只動了 F2 相關的 5 個檔案。

| 步驟 | 結果 |
|---|---|
| 單獨跑那一條（`--filter-method`） | 通過 → 不是產品問題 |
| `--max-threads 1` 跑整套 | 通過（394/394）→ 隔離問題 |

**根因**：產品碼 `SqlAssistChrome.cs:327-339` 的預覽區捲動處理常式開頭是

`Keyboard.PrimaryDevice` 讀的是**執行緒的 Win32 按鍵狀態**——實體鍵盤上壓著
Ctrl／Shift／Alt／Win 任一個，合成的 Home 就被當成有修飾鍵，處理常式提前 `return`，
`Handled` 留在 false，於是 `Assert.True(keyboard.Handled)` 紅掉。

**修法**：改用 repo 自己就有的 `tests/SqlAssist.Ssms22.Tests/TestKeyboardDevice.cs`
（`new TestKeyboardDevice()` 再傳進 `KeyEventArgs`），修飾鍵由測試指定，不再依賴 OS 狀態。
產品碼不動。同一個檔案另一處（約 667 行）本來就用了這個裝置，只有那一行漏掉。

**歸類**：這是與「行程共用靜態欄位」**症狀相同、成因不同**的第二類偶發紅燈——單獨跑與
`--max-threads 1` 都是綠的，但加 `[Collection]` 治不好。已寫進 `docs/rules-code.md`
的「品質與公開內容」與 skill `sqlassist-ssms22-tests`。

## 審 F2 時找到的第二個缺陷：主出現處索引算錯（潛在）

`SqlVariableRenameSession` 建構子的追蹤區段迴圈**邊找邊用** `primary`：

```csharp
var primary = 0;
for (var index = 0; index < spans.Length; index++)
{
    if (target.NameStarts[index] == target.NameStart) primary = index;   // 先更新
    spans[index] = ... index == primary ? EdgeInclusive : EdgeExclusive; // 再用
}
```

游標那一處**不是第一處**時（`NameStarts = [10, 50, 90]`、游標在 50），index 0 讀到的還是
初始值 `primary = 0`，於是**排主出現處前面的那些會誤用 `EdgeInclusive`**。

**影響面**：目前是潛在而非現行故障——`Replace` 只讀區段位置、不讀區段文字，而編輯都發生在
主出現處，其他出現處的邊界不會被動到。但它與程式碼自己的註解（「游標那一處…其餘的由我們
整段換掉」）不一致，且 `EdgeInclusive` 的語意就是「邊界被插入時跟著長」。

**修法（含架構調整）**：把主出現處的定位搬進 Core——`SqlVariableRename.FindAt` 當場記下
`primaryIndex = starts.Count`（游標那個詞法單元的索引等於 `index`），新增
`SqlVariableRenameTarget.PrimaryIndex`；編輯器那一層改成 `index == target.PrimaryIndex`，
不再自己搜尋。理由：定位是「只看文字就判斷得出來」的那一半，而 Core 那一半**測得到**，
編輯器那一層連不到 SSMS 服務。

**測試**：`SqlVariableRenameTests.主出現處的索引跟著游標走`（Theory，4 個用例：游標在第一／
第二／第三處，以及混大小寫 `@READERID`），同時斷言不變式 `NameStart == NameStarts[PrimaryIndex]`。

**負向驗證**：把 Core 改成 `primaryIndex = 0` → 4 個用例紅 3 個（預期 0 那個當然仍過）；
還原後全綠。

## 兩個「查了但沒動」的結論（免得重複嘗試）

**1. `SqlSnippetSurroundKeys` 在本 repo 的測試架構下測不到。** 那張殼層命令↔按鍵對照表

### 後續：拆 `themes.md` 這件事被倉庫自己禁止（我的推薦是錯的）
