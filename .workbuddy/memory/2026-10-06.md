# 2026-10-06

## EXEC 展開時避開同批次的同名變數

需求：`在 exec 後展開存儲過程後，如果整個編輯器裡有相同的變數，就改成合適的變數名稱`。

### 為什麼要做

展開出來的是 `DECLARE @x AS …`，而 `@x` 可能早就被同批次的其他地方宣告過了。
兩份 `DECLARE` 同名**不會有編譯錯誤**——第二句只是把第一句的值覆蓋掉。症狀是展開
之後那一句跑得動，卻把使用者原本的變數值改掉了，而畫面上只看得出多了一段宣告。
`where` 這種常見名字尤其容易踩到。

### 動手前對齊的三個分叉

| 分叉 | 決定 |
|---|---|
| 比對範圍 | **同一批次**（`GO` 之間）——沿用就地改名的界線，不是整份文件 |
| 改名策略 | **自動加數字後綴** `@LoanId` → `@LoanId1` → `@LoanId2` |
| 開關 | **要**，設定頁「插入與展開」新增一項，預設開啟 |

使用者選批次而非全文是對的：跨 `GO` 同名的 `@變數` 是另一個變數，避開它只會讓名字
多一個沒必要的後綴。

### 關鍵取捨

**批次界線的判定是逐字比對 + 獨占一行，不是問詞法單元是不是識別字。**
`GO 3`、`GO -- 註解` 算分隔；`SELECT 1 GO`、`'GO'`、`-- GO`、`GOTO` 不算。
「同一行的 `GO` 不切」讓兩個批次合成一個，**方向是保守的**——多收一個變數只是多一個
後綴，漏收一個真的變數才是安靜出錯的那一邊。這與 ScriptDom 的判定在同一行 `GO`
這種寫法上不一致，是刻意的。

## 修正：改名改到不該改的名字

回饋：`调整变量的名称,不需要调整存储过程的名称`。

第一版把「撞名的參數」整格換掉，於是 `EXEC dbo.usp_P @LoanId = @LoanId` 這一行
**等號左邊**的模組參數名也跟著變成 `@LoanId1`。那一句於是找不到對應的參數
（錯誤 8145），而畫面上只看得出名字多了一個數字。

### 根因

`SqlProcedureCallText` 拿 `parameter.Name` **同時填左右兩側**：

```csharp
assignments[index] = $"{parameter.Name} = {parameter.Name}";
```

左邊是**模組簽章**裡的名字（定義決定，呼叫端改不動），右邊才是**我們的**區域變數。
兩者共用一格，於是為了避開撞名而改掉 `Name`，連左邊也一起改了。

### 修法

`SqlStatementParameter` 新增 `VariableName`（省略時等於 `Name`），四個位置各用各的：

| 位置 | 用哪一個 |
|---|---|
| `DECLARE` 名稱 | `VariableName` |
| 呼叫等號**左邊** | `Name`（模組簽章，原樣） |
| 呼叫等號**右邊** | `VariableName` |
| `SELECT` 段 | `VariableName` |

同時把整批改名抽成 `SqlVariableNames.Avoid(parameters, sql, position)`（Core、純文字）。

### 教訓

**第一版把改名邏輯留在 VSIX 層（`SqlCommitExpansions.AvoidNameCollisions`），
`SqlAssist.Ssms22.Tests` 根本沒編到那個檔，所以測試碰不到——這正是 bug 溜過去的原因。**
Core 的 `InternalsVisibleTo` 有 `SqlAssist.Ssms22.Tests`，但 csproj 沒有把
`Completion/SqlCommitExpansions.cs` 連結進來。判準：**會被測到的邏輯就放到 Core**，
留在 VSIX 層等於沒有回歸保護。這一輪把邏輯抽到 Core 後補了 6 條 `Avoid` 測試。

另外兩個小的：`variableName` 用 `string.IsNullOrEmpty` 會讓 netstandard2.0 的
nullable 分析判成可能為 null（`CS8601`/`CS8618`），要寫 `x is null || x.Length == 0`；
還有一條測試自己算錯——`@x` 撞名換成 `@x1` 之後，本來叫 `@x1` 的參數要再讓到
`@x11`，不是 `@x2`（實作才對，測試期望錯了）。
